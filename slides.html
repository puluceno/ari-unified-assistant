So one chat window needs real work: the same user in every system, routing to the right system, safety checks that every team gets, and one log of every decision. It is not "just plumbing".

One entry point: yes. Customers should not need to know which team owns what. One brain: no. My team owns the chat. Each system keeps its own access rules.

The four teams already building

  • Nobody in the brief mentions them. This project has the potential to cancel other people's work, and that is the hardest part of shipping it.
  • I have lived this at Microsoft: my team was asked to build something, and a week later we found another team building the same thing.
  • First move: visit each team. What did you build, what worked? Show me your real user questions and logs.
  • Their work is not thrown away: each team becomes the owner of its domain agent. From building a chat window to owning a capability.
  • They don't report to me. So first I'd ask Dana: which senior leader backs this project, and who makes the final decision when teams disagree?

2 · What I'd push back on, and what I'd ask Dana

A good start. I believe there are four gaps

What the brief leaves out

  • Phase 2 has already started. Creating a ticket changes data. So: Ari offers, the user confirms, then Ari creates it. Later actions use the same pattern.
  • "80% ticket deflection" is easy to fake: make tickets hard to create. And bugs and outages always need a ticket.
    Better main metric: the user says the problem is solved, and does not come back about it within X days (X agreed with the stakeholders). We still count tickets, but we don't target them.
  • "Answer anything" must include "I don't know". For finance users, an honest "I don't know" builds more trust than a guess.
  • GPT-4o: OK to start with it. The model can be changed by configuration, and tests decide later.

Questions for Dana, and what I do with the answer

3 · Approach

The model proposes, code decides

Ari widgetinside the product page, so the user is already logged in
→
Hub (AI Platform team)
1 Identify the user
2 Input guard
3 Classify model
4 Decide code
5 Compose model
6 Number check code
→
Domain agents (domain teams)Omni · Help center · Forecasting · Onboarding
the same contract for all

Why this shape

  • The model only suggests where the question goes, and writes the answer. Code decides what happens. I can test it without a model.
  • Every domain returns the same thing: data, what was measured, source, time. A new domain does not change the router.
  • A ticket is created only after the user says yes.
  • The model can be changed by configuration.

Who owns what

  • My team: the chat, login, routing, safety checks, logs, tests.
  • Domain teams: correct answers for their area, and their own test questions. They join after passing our tests, for example: "What is my EUR exposure?" returns Omni's exact number; a Globex user never gets Acme's data.
  • The team: first see who is already there, and whether people in other teams want to join this effort. Then hire, if we need to.

Weak points

  • Assumes a logged-in customer. A public help site would get articles only.
  • Two model calls per answer: slower, and costs more.
  • One system per question, so mixed questions get half an answer.
  • The number check can't see if Omni ran the wrong query.
  • If the hub is down, Ari is down for everyone.

4 · Six weeks to the advisory board, and how I'd know it's working

Six weeks: show less, but show it working

Six weeks is short for a new team. Real safety checks and real testing take time.

What I'd show in six weeks (test data, one product page)

  • Help-center answers, with a link to the article.
  • Tickets: Ari offers, the user says yes, the conversation is attached.
  • Omni: about ten common questions (cash, FX exposure). Every number shows its source and time.
  • Shown as a preview: no release date, no actions promised.

Not in six weeks

  • Real customer data · actions (approve, pay) · forecasting and onboarding · more product pages · "ask anything" · full test automation and monitoring.

After six weeks

  • A test set of real questions from the four teams, with the right answer written down. Enough to cover each type of question a few times.
  • It runs on every change to a prompt or model. Track three things: right system? right number? "I don't know" when it should?
  • Thumbs up / thumbs down on every answer, so users tell us what works.
  • Every decision is logged for our team (users don't see it), so we can see why an answer went wrong.

Later in phase 1

  • The tests block the release if they fail.
  • A few known questions once a day against a test account, to catch changes in Omni we don't control.
  • A "this is wrong" button that goes to the domain team.
  • A ticket right after an answer = probably a wrong answer.

5 · What worries me, and where the demo stands

Users trust what they can check

What worries me

  • Omni. Highest risk, and nobody can tell me how often it reads a question wrong. A wrong number looks exactly like a right one. So Ari never retypes numbers: if a number is not in Omni's data, Ari shows the raw data. And every number shows what was measured, the source and the time.
  • One customer seeing another's data. The model never decides who sees what. Each system checks the user's permissions. In the demo, only the user's company is passed.
  • Prompt injection. The model has no power: it only reads, and a ticket needs the user's "yes".
  • Six weeks growing into "ask anything". A clear scope for each release, and a prioritised roadmap.

The demo

  • Java 25 + Spring Boot, ~540 lines in 7 files, 7 tests that run without a model. The model call is real (Azure OpenAI). Omni, help center and Jira are mocks. Every answer shows "How Ari decided".
  • Not built: real user permissions (the demo trusts the chat app's user header, protected by an API key), word-by-word streaming, questions that need two systems.
  • What I found by testing it:
    • "My EUR exposure looks too low; how do I connect a missing bank account?" needs two systems. Ari picks one: half an answer.
    • "EUR/USD rate at close yesterday?" goes to Omni at 0.67. There is no "not supported" option, and the 0.6 limit is a guess.
    • "What is my EUR exposure?" then "and GBP?": Ari asks what I mean. It only reads the last message.
  • Next two weeks: polish the code; add a new system by configuration, not new code; start the test set of real questions; start real user permissions; handle questions that fit two systems, or none.
